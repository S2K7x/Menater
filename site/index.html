01 Why

An AI that decides alone is an AI reading text an attacker wrote.

Security tools raise far more alerts than anyone can read, so triaging them automatically is not really optional. But an alert is text an attacker composed, and a model that can both read it and act on it can be told what to do by it. MENATER separates those two powers: the model reads and proposes, a human holds the trigger.

It says what it cannot see, instead of filling the gap.

The four rules that follow from it 4 rules · enforced in code
  • Never fill a gap with a default A missing value is shown as missing — —, never 0, never N/A, never a guess. And rejecting an alert because a field is absent is the same mistake in its harshest form: it replaces the alert with nothing.
  • Silence is never consent An approval request that times out executes nothing — it escalates. Missing configuration cannot enable execution either: watch-only mode is the default, and only the exact word false turns it off.
  • A failure must never show green A chain that ran and passed zero items is Broken, not Done. A verdict of clean requires at least one intelligence source that actually answered — nobody looking is Not asked, which is a different sentence.
  • No irreversible action without a human The list of things the console can execute is closed at four entries. Nothing else is implementable — not even behind an approval — and no tuning rule can reach it.
02 How it works

An alert comes in. Five steps later, you decide.

The same five steps run for every alert, in the same order, and each one writes down what it did. Step four is a person — and nothing past it happens without them.

  1. Step 1 An alert arrives From your SIEM, by webhook or by polling. Checked, and deduplicated so the same alert is never triaged twice.
  2. Step 2 Context is gathered Is this address known bad? Has this password leaked? A source with no key is marked not asked, never guessed.
  3. Step 3 The AI proposes A verdict, a confidence score, and the reasoning behind both. A proposal — never an order.
  4. Step 4 You You decide The proposal reaches you in the console, and on Slack or Discord if you want it there. Until you answer, nothing runs.
  5. Step 5 It is written down One row in a log that can be added to and never edited, sealed to the row before it. Tampering shows.
  • You approve The one action you approved runs, and only that one.
  • You refuse Nothing runs. The refusal is recorded, and it is what measures the AI.
  • You do not answer Nothing runs. It escalates to a human instead of timing out quietly.

Out of the box, step 4 never even fires. The console starts in watch-only mode: it records what it would have proposed and executes nothing at all, until your team has looked at enough real alerts to trust it.

What the engine underneath actually does 6 workflows · typed handoffs

MENATER runs its own engine. There is no workflow platform to install and no second product that has to be reachable for an alert to be triaged — so a workflow cannot be half-deployed, renamed in an editor, or left unpublished. The five steps above are five workflows with a fixed, typed input and output; a sixth is the error handler, declared on the other five and called only from their failure branches.

  • A junction waits A step with several inputs does not start when one of them has answered. Enrichment would otherwise assemble a third of its sources — with no error, no trace, and a plausible result.
  • Retry, then a named failure Every external call retries with backoff, honouring a suggested wait as a floor rather than undercutting it. When it still fails, it fails by name: a source that was not asked is not a source that said nothing.
  • The unreduced view The queue stitches runs into cases, and two kinds of failure disappear in that reduction. A separate screen shows them unreduced — broken chains, runs attached to no alert, a searchable log, and a replay that refuses when the original alert is unknown.
03 What you get

Three screens do most of the work.

One console, one address, one password. There are ten tabs in it, but on an ordinary day you live in three of them.

The queue

Every alert, most urgent first. Open a row and you get the whole story: what came in, what was found out, what the AI thinks, and what it wants to do.

Code scanning

The other half of the console reads your code and looks for the flaws an attacker would use — a folder, a file or a GitHub repository. Each finding says what can happen and how to fix it.

Lookup

Paste an address, a domain, a file hash or an e-mail and ask about it directly. The answer always says how many sources actually replied.

04 Guardrails

The list of things it will not do is the feature.

Four limits, each one written into the code rather than promised in a slide. They are what makes an AI safe to point at attacker-composed text all day.

It watches before it acts

A new install executes nothing. It records the decision it would have made, and waits until your team has measured, over real alerts, how often they disagreed with it. That measurement is the gate, not a date.

Four actions, and no fifth

Isolate a machine temporarily — with an expiry and an automatic undo — open a ticket, escalate, or close as a false positive. Nothing else can be added. And isolation refuses to run when it has no machine to name.

The chat assistant cannot act

A panel answers questions about your own installation using seven read-only lookups and nothing else. An instruction hidden in a log arrives at a model that has no way to obey it.

Everything stays on your machine

Three containers on your own host, one port published. Your alerts go to the model you chose with the key you supplied, and nowhere else. No account, no telemetry, no vendor cloud in the path.

The conditions those numbers were taken under one machine · reproducible

Run against docker compose up and nothing else. This is a QA pass on one machine, not a published benchmark; the point is that it is reproducible and that the conditions are stated. It found eight defects, and they were fixed — three worth naming: the entry point told senders their refused alerts had been accepted; the deduplication insert was not safe against a burst and answered an error; and the audit verifier reported broken links on healthy rows. A verifier that cries wolf is one an auditor stops believing, which would hide a real deletion in the noise.

05 Install

Two commands, on any host with Docker.

Nothing else to install: no database to configure, no schema to apply by hand, no second machine. The database and the scanner are reachable only from inside the stack.

# fill in the two passwords
cp .env.example .env

# database + console + code scanning
docker compose up -d --build

→ http://localhost:4400

It comes up in three minutes and triages nothing. That is not a fault: each of the four things below is a choice the console refuses to make for you, and a checklist on the settings page tracks all four until they are done.

Threat-intelligence keys and chat notifications are optional — a source with no key shows as Not asked rather than being filled in.

06 Limits

What it does not do.

Said here for the same reason the console says it: a page that lists only what works is a green that was never earned.

  • The two halves do not talk A code scan creates no alert in the queue, and an alert starts no scan. They share an interface and a login; connecting them is the next priority.
  • The login identifies nobody Access is a single password. It protects the console; it does not tell one approver from another, and the audit row says exactly that rather than implying a name it does not have.
  • It is a project, not a product Self-hosted, open source, no support contract and no company behind it. Read the code before you point it at anything that matters — which is the right thing to do with any of these.
